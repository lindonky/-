# “行步如飞”产品需求基线与开发路线

> 文档状态：需求基线 v0.1
>
> 整理日期：2026-08-12
>
> 需求来源：《行步如飞——水下康复下肢训练仪》21 页演示文稿、两张 UI 局部截图、当前 ESP32-S3 固件与 Android App 源码。
>
> 用途：代替反复读取整份 PPT，作为后续固件、网页 UI、Android App 和训练算法开发的长期上下文。

## 1. 一句话产品定义

“行步如飞”是一套面向水下下肢康复训练的可穿戴机电系统：通过姿态传感器采集腿部运动，使用三路水下动力单元提供助力、主动或阻抗训练，并为患者和治疗人员提供实时训练反馈、训练记录和阶段报告。

当前工程已经完成“设备控制器”，下一阶段要补齐“训练系统”：

```text
现有：姿态采集 → 三模式控制 → 急停 → 手机网页控制
目标：姿态采集 → 步态事件识别 → 训练会话 → 指标计算 → 实时 UI → 历史报告
```

## 2. PPT 信息提炼

### 2.1 产品动机

PPT 第 4–7 页认为传统康复设备存在以下问题：

- 设备价格高、体积或负重较大。
- 训练重复枯燥，患者主动性和依从性不足。
- 训练评价依赖治疗人员经验，缺少连续、可量化的数据。
- 陆上训练对关节有较大负担，并存在跌倒风险。
- 水中浮力能够减轻身体负担，水阻力能够增加肌肉负荷，同时有利于关节保护、平衡与协调训练。

这些内容构成产品方向，但不等同于已经得到本设备临床验证的结论。

### 2.2 PPT 定义的系统组成

PPT 第 9 页把系统分成四部分：

1. 机械穿戴系统：轻量、贴合人体关节轨迹，提供支撑和动力。
2. 姿态感知系统：六维传感器采集肢体姿态和运动数据。
3. 软件交互系统：医患查看实时数据、阶段评价和训练报告。
4. 云端数据平台：设备接入、状态监控、数据同步和远程管理。

当前工程已经部分实现第 2、3 项；第 4 项仍是规划，尚无后端服务。

### 2.3 PPT 预期的软件功能

PPT 第 13、14、17、19 页及用户提供的局部截图共同表达了以下软件目标：

- 设备连接状态及训练模式显示。
- 治疗方案和训练计划配置。
- 主动模式训练的开始、结束和持续时间。
- 实时显示步数、步频、动作正确率、摆动期时间和负重期时间。
- 调整治疗强度、电机速度、运动范围和训练时长。
- 训练记录按日期查询。
- 当日训练与历史训练对比，如步数变化、正确率变化。
- 生成医生建议或阶段性报告。
- 患者档案、症状、训练阶段和综合评价。
- 未来通过移动端、Web 管理端和云端数据库进行同步。

PPT 中出现的姓名、年龄、946 步、70% 正确率、14:30、16:30、3.8 km/h 等均为 UI 展示样例，不是现有设备实测数据，也不能直接作为算法目标值。

### 2.4 PPT 预期的安全功能

PPT 第 15、20 页提出：

- 姿态偏离时进行自动矫正。
- 加速度异常时识别跌倒。
- 跌倒后停止三个电机。
- 蜂鸣器报警并向手机发送告警。

当前固件已经具备姿态稳定、IMU 超时停机、超角度停机和闩锁式急停，但尚未实现经过验证的跌倒检测，也没有蜂鸣器硬件定义。

## 3. PPT 与真实工程的技术差异

后续开发以真实工程为准，不能照搬 PPT 中的旧技术名词。

| PPT 表述 | 当前真实工程 | 处理原则 |
|---|---|---|
| STM32 主控 | ESP32-S3 | 继续使用 ESP32-S3 |
| MPU9250 | JY61P | 继续使用已接入的 JY61P |
| 蓝牙 HC-05 | ESP32-S3 BLE NUS + Wi-Fi | S3 不支持经典蓝牙，不能使用 HC-05 方案描述 |
| PID | 当前为三段式 PD | 先验证现有控制律，再决定是否增加积分项 |
| MQTT/EMQX/MySQL/Redis/云端 | 尚未实现 | 放到后期，不阻塞本地训练闭环 |
| 20 米水深工作 | 未见认证或验证记录 | 不作为当前版本能力声明 |
| 跌倒检测已完成 | 尚未实现 | 必须采样、标定和误报测试后才能声明 |
| 步态准确率已实现 | 只有 UI 示例值 | 先定义评分标准，再实现和验证 |
| 医生建议 | 尚无医生规则或模型 | 不能自动生成医学建议；初期仅显示客观训练数据 |

## 4. 当前工程基线

### 4.1 已实现

- ESP32-S3 控制三路 ESC：左舵、推进、右舵。
- JY61P UART 数据解析。
- 助力、主动、阻抗三模式。
- 姿态稳定、IMU 超时保护、超角度停止。
- 闩锁式急停：`STOP` 后必须 `START` 才能恢复。
- Wi-Fi SoftAP、HTTP API、内嵌网页。
- UART、HTTP、BLE NUS 共用文本指令协议。
- Android App 连接热点并通过 WebView 打开控制页。
- 3D 腿部姿态显示。

### 4.2 JY61P 已经采集的数据

当前 `jy61p` 驱动已经解析并保存：

- 姿态角：`rollDeg`、`pitchDeg`、`yawDeg`。
- 三轴角速度：`gyroXDps`、`gyroYDps`、`gyroZDps`。
- 三轴加速度：`accelXG`、`accelYG`、`accelZG`。
- 样本序号：`sequence`。
- 时间戳：`timestampMs`。
- 数据有效性、有效帧数和校验错误数。

因此下一阶段不是重新编写传感器协议，而是建立完整的数据管线。

### 4.3 当前数据管线缺口

- `stabilize_status_t` 只保存姿态角、俯仰/横滚角速度，没有保存三轴加速度和 Z 轴角速度。
- `/api/status` 只返回一个字段 `g`，代表俯仰控制轴角速度，没有完整三轴向量。
- 网页每 500 ms 请求一次状态，2 Hz 数据不足以进行可靠的步态事件识别。
- 没有训练会话的开始、暂停、结束和编号。
- 没有步数、周期、步频、运动范围、稳定性等指标计算。
- 没有原始数据或会话摘要持久化。
- 没有历史报告页面。

## 5. 三种训练模式的产品定义

控制模式和训练统计应分层：控制模式决定动力输出；训练模块负责记录和评价。训练统计原则上可以覆盖三种模式，但第一阶段重点做主动模式。

### 5.1 助力模式 `assist`

当前控制：

- 俯仰误差控制中间推进器。
- 横滚误差控制左右舵差动。

目标功能：

- 记录患者在助力条件下完成的运动周期。
- 记录控制器介入量，用于区分患者动作与设备辅助。
- 后期可计算“平均辅助强度”和“辅助占比”。

### 5.2 主动模式 `active`

当前控制：

- 中间推进器保持固定基准输出。
- 左右舵继续做横滚稳定。

目标功能：

- 患者主动完成周期运动，系统实时计步并记录动作质量。
- 显示会话计时、步数、步频、运动范围、周期稳定性和估算的摆动/回位时间。
- 结束后生成本次训练摘要。

需要进一步确认：康复语义中的“主动模式”通常强调患者主动输出、设备少介入；当前“固定基准油门”是否符合真实训练意图，需要实机和治疗方案共同确认。第一阶段可以先保留控制律，只增加数据采集和统计，避免同时改变控制和评价两个变量。

### 5.3 阻抗模式 `impedance`

当前控制：

- 推进输出取俯仰控制输出的反向。
- 需要真正支持双向运行的电调才能产生物理阻力。

目标功能：

- 记录阻抗训练的周期、峰值角速度和运动范围。
- 记录指令阻抗强度；后期有电流或力传感器后，才能估算真实阻力或患者输出功。

当前不能把 PWM 指令值称为真实阻力、力矩或肌力。

## 6. 第一阶段训练指标

### 6.1 可在单个 JY61P 基础上实现

| 指标 | 推荐定义 | 实现状态 |
|---|---|---|
| 训练时长 | 会话开始至结束，扣除暂停时间 | 可直接实现 |
| 周期数/步数 | 完整通过一次抬腿—峰值—回位状态机计 1 次 | 需要算法和标定 |
| 步频 | 最近有效窗口内的周期数/分钟 | 需要算法 |
| 运动范围 ROM | 每周期主要运动轴最大角度减最小角度 | 需要算法 |
| 峰值角速度 | 每周期主要运动轴的最大绝对角速度 | 可计算 |
| 周期时长 | 相邻同相位事件之间的时间 | 可计算 |
| 抬腿时间 | 从离开中位到达峰值/反转的时间 | 可估算 |
| 回位时间 | 从峰值返回中位稳定区的时间 | 可估算 |
| 周期一致性 | 最近 N 个周期时长和 ROM 的变异程度 | 需要定义评分 |
| 安全事件 | 急停、IMU 超时、超角度、候选跌倒 | 可记录 |
| 控制介入量 | 控制输出绝对值的均值、峰值和持续比例 | 可计算 |

### 6.2 不能直接从单个 JY61P 可靠得到

- 左右腿独立步数和左右对称性：需要左右腿各自的传感器或明确的单侧安装定义。
- 精确步长、行走距离和 `km/h`：水下原地或辅助运动场景不能仅靠单 IMU 可靠积分得到。
- 真实负重期：需要足底压力、接触开关、力传感器，或者经过验证的多传感器模型。
- 患者输出力、力矩、肌力和能量消耗：需要力、电流、扭矩或生理传感器。
- 临床意义上的动作“正确率”：需要治疗人员给出动作模板、允许范围和评分规则，并完成数据验证。

### 6.3 “正确率”的临时处理

PPT 的 70% 正确率目前没有数学定义，不应直接实现为看起来精确的医学指标。

MVP 建议显示“动作稳定度”或“周期一致性”，并明确它只是工程评分。例如：

```text
周期合格：ROM、周期时长、峰值角速度均落在本次标定范围内。
周期一致性 = 合格周期数 / 有效周期数 × 100%
```

只有在治疗人员确认动作模板和阈值后，才将其命名为“动作达标率”；在临床验证前不使用“康复正确率”措辞。

## 7. 步态/周期识别算法建议

### 7.1 算法运行位置

步态事件识别应运行在 ESP32 内部，而不是运行在网页中：

- ESP32 已经有 10 ms 控制周期，可获得稳定的高频时间基准。
- 网页当前只有 500 ms HTTP 轮询，容易漏过峰值和相位变化。
- WebView 可能因为渲染、后台切换或网络抖动被限频。
- 安全事件和训练事件使用同一时间源，报告更可信。

UI 只接收训练摘要和降采样曲线。

### 7.2 推荐状态机

第一版以安装后的主运动轴为准，默认使用相对零位 `pitch` 和对应角速度：

```text
IDLE/中位稳定
  → LIFTING/抬腿：角度越过启动阈值且角速度方向正确
  → PEAK/峰值：角速度过零或角度达到局部最大
  → RETURNING/回位：角度向中位回落
  → SETTLED/稳定：回到中位窗口并保持最小时间
  → 完成 1 个有效周期
```

基础防抖规则：

- 启动角阈值和回位角阈值分开，形成迟滞。
- 设置最短/最长周期，排除抖动和长时间停顿。
- 设置事件不应期，避免同一峰值重复计数。
- IMU 超时、急停或超角度立即中止当前候选周期。
- 每个周期保留开始、峰值、结束时间和质量标志。

### 7.3 标定流程

在开始训练前增加简短标定：

1. 患者保持中立姿态，执行姿态归零。
2. 记录静止噪声 2–3 秒，估计角度和角速度噪声。
3. 可选：在治疗人员保护下完成 3–5 个示范周期。
4. 根据示范生成本次训练的 ROM、周期时长和角速度参考区间。
5. 将本次阈值与会话绑定，不直接覆盖系统安全阈值。

## 8. 数据架构建议

### 8.1 ESP32 实时层

新增独立 `training_session` 模块，不把训练统计塞进姿态控制器：

```text
JY61P parser
   ├── stabilize：控制和安全
   └── training_session：滤波、事件识别、会话统计
```

建议训练模块输入：

- 单调递增时间戳。
- 三轴姿态角。
- 三轴角速度。
- 三轴加速度。
- 当前模式、控制输出、急停和安全故障。

建议训练模块输出：

- 会话状态：idle/running/paused/finished/fault。
- 会话 ID、模式和时间。
- 周期数、有效/无效周期数。
- 当前步频、平均 ROM、平均周期时间。
- 抬腿/回位时间估算。
- 周期一致性评分。
- 最近事件和安全事件。

### 8.2 传输层

保留 `/api/status` 兼容现有控制页，逐步增加：

- 完整 IMU 字段：`gx/gy/gz`、`ax/ay/az`、`seq`、`age`。
- 训练状态端点：`GET /api/training/status`。
- 训练控制命令：`TRAIN START|PAUSE|RESUME|STOP|RESET`。
- 最近一段降采样曲线或批量样本端点，供图表使用。

不建议用 20–100 Hz 的单条 HTTP 轮询发送每个原始样本。可选方案：

1. ESP32 内部计算指标，网页 4–10 Hz 拉取摘要；优先实现。
2. 通过批量缓冲返回最近 N 个样本；适合绘制曲线。
3. 后期使用 WebSocket 推送；需要额外连接管理和可靠性测试。

### 8.3 持久化

- ESP32 RAM：保存当前会话和短曲线缓冲。
- ESP32 NVS：只保存少量配置和标定参数，避免高频写 Flash。
- 第一版本地历史：网页可使用 IndexedDB；清除 App 数据会丢失，需要明确提示。
- 正式 Android 历史：建议后续在 App 中使用 SQLite/Room，并支持 JSON/CSV 导出。
- 云端：在本地会话格式稳定后再设计，不要一开始引入 MQTT、MySQL 和 Redis。

## 9. UI 信息架构

### 9.1 设计原则

- 安全优先：急停始终可见，不能藏在菜单或工程设置里。
- 数据真实：传感器离线或指标未实现时显示 `--`，不能显示示例数字。
- 训练优先：患者训练页面只显示关键动作信息，工程滑块和原始指令放到独立高级页面。
- 单手操作：主要按钮面积足够大，适配潮湿环境和手机竖屏。
- 不依赖云端：与设备热点直连时必须可以完成训练和生成本地摘要。
- 报告可解释：每个评分都能追溯到明确的计算定义。

### 9.2 页面结构

#### A. 设备与模式首页

- 设备连接、IMU 在线、数据年龄、急停状态。
- 助力/主动/阻抗模式选择。
- 当前治疗参数摘要。
- “开始训练”入口。
- 固定急停按钮。

#### B. 实时训练页（第一阶段重点）

- 当前模式和训练计时。
- 大号步数/周期数。
- 当前步频。
- 动作稳定度/周期一致性环形图。
- ROM、抬腿时间、回位时间。
- 简化的姿态和角速度实时曲线。
- 当前相位：中位、抬腿、峰值、回位。
- 开始、暂停、结束。
- 固定急停；急停发生时暂停会话并记录安全事件，不清除已有数据。

#### C. 本次训练报告

- 模式、开始时间、有效训练时长。
- 有效周期、无效周期、平均步频。
- 平均 ROM、周期时长、峰值角速度。
- 周期一致性和安全事件。
- 与最近一次同模式训练对比；没有历史时不显示虚假变化。
- 导出 JSON/CSV；后期生成 PDF。

#### D. 历史记录

- 按日期和模式筛选。
- 周/月趋势：训练次数、周期数、ROM、周期一致性。
- 查看单次训练详情。

#### E. 治疗方案（后期）

- 训练阶段、频率、单次时长、目标模式。
- 动作项目和参数范围。
- 由治疗人员编辑，患者端只查看或执行。
- 训练计划完成/未完成记录。

#### F. 工程与诊断页

- 三路 PWM、手动滑块、摇杆、校准、原始命令。
- 三轴 IMU 原始数据、帧率、校验错误、数据年龄。
- 仅用于调试，不与患者训练主页面混排。

### 9.3 视觉方向

可继承 PPT 的蓝色 + 浅青色医疗科技风格，但重新建立统一组件规范：

- 主色：深蓝，用于标题、主要动作和正常连接状态。
- 辅色：浅青，用于图表、进度和次级操作。
- 橙色：警告和未达标，不用于普通按钮。
- 红色：只用于急停和严重故障。
- 白色卡片、清晰间距、少量阴影；避免把所有信息都做成同等权重的卡片。

## 10. Web UI、Android 与 LVGL 的技术选择

### 10.1 当前推荐：继续使用 Web UI

当前设备没有本地显示屏，手机 App 本质上是 Wi-Fi 连接器和 WebView。现阶段继续使用 HTML/CSS/JavaScript 最合适：

- 不改变现有手机控制链路。
- 同一页面可在 Android App 和普通浏览器中运行。
- 图表、历史记录和响应式布局比嵌入式 GUI 更容易实现。
- 不需要为 UI 再接入一套显示屏驱动、触摸驱动和显存管理。

建议把当前单个约 62 KB 的 `web_page.html` 逐步拆分为可维护的模块：

```text
web/
├── index.html
├── styles.css
├── app.js
├── training.js
├── charts.js
└── engineering.js
```

构建时仍可作为文本资源内嵌到固件。

### 10.2 LVGL 的适用场景

用户提供的 LVGL 库适合作为未来本地触摸屏方案的参考。如果后续硬件增加 LCD 和触摸屏，LVGL 可用于：

- 本地模式选择和训练启停。
- 大号训练计时、步数和状态显示。
- 离开手机时的独立急停辅助界面。

在没有本地屏幕的当前硬件上，不建议用 LVGL 重写手机 UI。LVGL 不是 Android/WebView UI 框架，也不能直接替代现有网页。

## 11. 跌倒检测的实现边界

JY61P 已有加速度数据，可以做“候选异常事件”，但水中环境会显著改变加速度、冲击和姿态变化模式。第一版不能仅凭一个瞬时阈值宣称跌倒。

建议分级：

1. 异常候选：合加速度、姿态变化和角速度同时越界。
2. 持续确认：异常后姿态保持在危险范围或无有效动作。
3. 立即安全动作：进入急停闩锁，停止三路输出。
4. UI 告警：显示原因、时间和传感器数据，要求人工确认。
5. 误报验证：陆地、水下、正常快速动作和传感器松动分别采样。

是否增加蜂鸣器、独立硬件急停或第二传感器，需要在硬件设计阶段确认。

## 12. 分阶段开发路线

### 阶段 1：数据管线和实时训练 MVP

- 在状态结构中补齐三轴角速度、三轴加速度、序号和数据年龄。
- 新增训练会话模块及 `TRAIN` 命令。
- 实现主动模式的周期状态机。
- 输出训练时长、周期数、步频、ROM、抬腿/回位时间和一致性。
- 重构实时训练 UI，保留急停和工程控制入口。
- 使用人工计数视频或串口回放验证计步误差。

### 阶段 2：本地报告和历史

- 本次训练报告。
- IndexedDB 或 Android SQLite/Room 持久化。
- 历史筛选和趋势图。
- JSON/CSV 导出。

### 阶段 3：三模式训练分析

- 助力模式增加控制介入量。
- 阻抗模式增加指令阻抗强度和周期特征。
- 统一同一患者、同一模式的趋势比较。

### 阶段 4：治疗方案和多角色

- 患者档案与治疗人员账号。
- 训练计划、目标范围和完成记录。
- 治疗人员确认后的动作达标规则。
- Android 原生数据库和更可靠的文件导出。

### 阶段 5：云端和扩展传感器

- 设备注册、远程同步和 Web 管理端。
- 双腿 IMU、足底压力或力/电流传感器。
- 左右对称性、真实支撑期和动力学指标。
- 经数据验证的跌倒检测。

## 13. 阶段 1 验收标准

- IMU 离线时所有实时指标显示 `--`，不能保留旧数据伪装在线。
- 步数来自 ESP32 实时状态机，不依赖 500 ms 网页轮询计数。
- 每个周期能追溯到开始、峰值和结束事件。
- 急停在任何 UI 页面都能一步触发，触发后训练会话暂停并记录事件。
- 模式切换不能自动开始训练；训练开始必须由明确操作触发。
- 结束训练后数据不再变化，报告与结束瞬间一致。
- 至少用一组人工标注动作验证计数、漏计、重复计数和异常动作排除。
- UI 在常见 360–430 px 手机宽度下无横向滚动、遮挡或误触区域。
- 不显示未经定义或未经验证的“正确率、负重时间、速度、肌力”等指标。
- 工程控制页仍保留校准、原始命令和三路输出诊断能力。

## 14. 开发前必须确认的问题

这些问题会改变算法定义，但不妨碍先完成数据管线和 UI 骨架：

1. JY61P 最终安装在左腿、右腿、脚、小腿还是设备主体？安装方向是什么？
2. 当前设备是单腿训练还是双腿训练？是否计划每条腿安装独立传感器？
3. “一步”在实际水下训练中指完整抬腿—回位周期，还是左右腿各触地一次？
4. 主动模式的固定基础油门是否符合训练意图，还是应随患者动作跟随或只做姿态稳定？
5. “正确/达标动作”的参考由谁给出：固定角度范围、治疗人员示范，还是患者个人基线？
6. PPT 中的“摆动期/负重期”是否必须作为临床指标？若必须，是否允许增加足底压力或接触传感器？
7. 第一版训练记录只保存在手机本地是否可接受？何时需要多患者、医生端和云同步？
8. 是否计划增加本地 LCD/触摸屏？只有明确增加屏幕时才启动 LVGL 方案。

## 15. 当前推荐的下一项开发

优先完成“阶段 1A：完整遥测接口”，不先重做所有页面：

1. 将 JY61P 三轴姿态、三轴角速度、三轴加速度和数据健康信息完整暴露。
2. 建立独立训练会话数据结构，但暂不做医学评分。
3. 增加实时曲线和数据诊断页，用实机采集一批主动训练样本。
4. 根据真实曲线确定主运动轴、阈值、周期状态机和 UI 指标。
5. 样本稳定后，再实现 PPT 风格的主动训练主界面和训练报告。

这样可以避免先把 UI 做得很漂亮，却让步数、正确率和周期时间建立在未经验证的数据上。

## 16. 文档维护规则

- 本文档是产品需求和实现边界的主入口。
- 控制细节和接线仍以 `docs/HANDOVER.md` 为准。
